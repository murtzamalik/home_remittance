1.  Overview & Background 
 
The transaction volume of RTGS has been significant ly increased and is expected to be increased furthe r due to the decision taken by 
SBP to allow customers’ funds transfers for lower li mits. Therefore, considering the increasing trend in RTGS transfers SBP has initiated 
STP project to automate the RTGS payments to minimize manual workload of customers’ requests for RTGS. 
 
This will not only help us in reducing the TAT due to duplicate efforts put in by the relevant departments due to manual posting in core 
banking system and PRISM but will also help us in i mproving our processing capabilities to manage addi tional transactional volume 
within the window allowed by SBP for RTGS payments. 
 
Straight through Processing (STP) is an initiative used in the financial world to optimize the speed a t which transactions are processed. 
This is performed by allowing information that has been electronically entered to be transferred from one party to another in the 
settlement process without the need for re-keying the same pieces of information repeatedly over the life cycle of the transaction. 
 
About RTGS System  
RTGS system started its operations in July 2008. Since its inception, enrollment of the participants is growing and volume of transactions 
is also increasing.  
 
Payment System Department has also introduced Customer Transfers (MT103) and Multiple Credit Customer Transfer (MT102). This has 
further increased volume of transactions. 
 
Currently, RTGS Participants are entering transactions in RTGS system manually using RTGS Client workplaces installed at their own 
premises. Same transactions they also have to re-enter in their Core Banking System through its own workplaces. Multiple re-keying is 
inefficient and error prone. Soon it will also be impractical to enter all these transactions manually due to increase in volume. 
 
Therefore, it was decided to introduce STP (Straight Through Processing) to deal with the above mentioned issues. STP will electronically 
connect Participant Core Banking system with RTGS system using standard interfaces that are already provided with the RTGS system. 
 
In this connection, Participants needs to develop an Integration Software that can pick up information from their Core Banking System 
and transfers it to RTGS system for processing and vice versa.

2.  Bank Requirement Scope 
 
However, since the bank has opted option of File Ada pter without “Controller”; therefore it is essentia l to develop “INTEGRATION 
SOFTWARE” to cater the need of “controller” which cu rrently provided by SBP as part of PRISM to perform  multiple functions, which 
includes but not limited to authorization of MT102, MT103, MT202, Balance enquiry, monitoring of inflows a nd outflows, free format 
messaging and any other functionality which is currently available in the PRISM Controller provided by SBP. 
 
The integration software should have the capability of interfacing with partner applications i.e. Remit Home System, CMS Application, T-
24 and any other application which requires to be integrated with integration software. 
 
Upon receiving the RTGS instructions from any of th e partner application, the integration software, shou ld convert the message based 
on its payment type (as per SBP’ prescribed formats of MT-102, MT-103 and MT-202) and push the outward MTs to PRISM by following 
all the relevant protocols to meet SBP’ requirements. Similarly, the integration software should have the capability to receive incoming 
RTGS received via PRISM from other banks for various departments/customers of the bank.

4.  Integration with Banking Modules 
 
Banking applications (Home remittances, Treasury etc) 
 
• Send data by calling API method provided by Integrator. 
• Get data acceptance response from Integrator, acknowledging that transactions have been received. 
• Get the status information of the data send by calling status method of Integrator. 
• Get data by calling API method provided by Integrator. 
• Update the status of transactions that they have received (Incoming transactions) by calling API method.
