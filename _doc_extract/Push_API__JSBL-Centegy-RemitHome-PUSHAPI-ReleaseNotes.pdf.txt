RemitHome Web Service API (Push Model) 
Introduction: 
 
The RemitHome Web Service API (Push Model) enables third party applications to connect 
with RemitHome and perform validations, inquiries and execute transactions.  
 
RemitHome Web Service API support s both real time and delayed transfer/processing of 
funds into a beneficiary bank account (direct credit) or for cash over the counter payments. 
With RemitHome web service API, remittin g entities will be able to effect the payments  
directly into HBL’s core banking system and get acknowledgements. 
 
Intended Audience: 
 
Although, this document is primarily targeted for programmers, it also has some content for 
business users. This document presents the detail  of integration with the RemitHome Web 
Service API(Push Model) .  
 
WSDL Location 
 
WSDL file is provided separately along with this document . The actual web -service URL will 
be communicated to the partner before the commencement of testi ng and before going live 
(for production site). 
 
Test and Production Environments 
 
In addition to the production environment, a separate test environment will be made 
available to the partners upon request to facilitate testing of their client application. 
Network Connectivity 
 
The web-service interface (for both test and production systems) would be made available to 
the partner on the Internet accessible via a public IP address . Only the designated partner’s 
source IP addresses will be white -listed at HBL’s firewall and the web -service will not be 
accessible to any other IP. The web -service will listen on a custom SSL port. The SSL 
certificate will be shared in advance with the partner.

Business Scope  
 
In general, transaction processing is divided into two processing modes, (can be define d in 
transaction request). 
 
a) Real Time Transaction Processing. 
b) Delayed Transaction Processing. 
RemitHome API by default attempts to process tra nsaction in real -time mode , however, if 
the transaction cannot be processed in real -time, then it will be moved to delayed 
transaction processing mode  (if instructed by the requester application).  Response to 
requesting application will send accordingly. 
 
Transaction can be move to Delayed Transaction Processing mode for following reasons. 
 
 Invalid or incomplete account information [Only For Transaction Mode=2] 
 Transactions belonging to other local banks that could not provide real -time 
interface. 
 Delay in AML Verification. 
 
In latest patch of PUSH API,  a new value [ Transaction Mode=3] has been introduced for 
delay mode processing. Own Account transactions sent with this mode value must contain 
valid Account Information for smooth processing otherwise PUSH API would be reject the 
transaction even in the delay mode. 
 
Following types of payments are covered in RemitHome API: 
 Cash over the Counter (COTC) transactions: In this case  Remitting Entity will forward 
COTC transactions to RemitHome web server API and transaction will be ready for 
collection by beneficiary from any branch.  
 Account Credit transactions: In this case remitting entity will provide credit directly to 
beneficiary account including non-HBL local  bank accounts  after verifica tion of 
beneficiary account details.  
o HBL customer accounts. 
o Third-party bank beneficiary accounts

Transaction Set: 
RemitHome Web Service API (Push Model) provides following set of web methods for third 
party integration. 
 
Category Web Method Name Description 
General Inquiries FetchAccountTitle To fetch title against account holder bank id 
and A/c number. 
 BalanceInquiry  Remitting Entity A/c balance inquiry. 
 BankCodes To get list of allowed third party banks 
Transaction Inquiry GetTransactionStatus  To get status of previously sent transactions. 
Transactions Request TransfertoCOTC  To forward cash over the counter transaction. 
 TransfertoAccount  To forward direct credit transaction 
 
Process Flow 
 RemitHome web service API exposes corresponding classes against each web methods  
for submission of requests and retrieval of responses. 
 
 Each Request authenticated by following Parameters. 
 Agent ID.   (Provided by Bank) 
 User ID.     (Provided by Bank) 
 Password. (Provided by Bank) 
 
 After authentication gets successful then the corresponding activity executed, otherwise 
“Authentication Failure Response” sent in response.  
 
 Each request is acknowledged by sending valid Response Code and Response Message to 
requester, which shows activity status either Successful or Failure.

General Information  
 
Request 
All methods expect a single Object as parameter. This Object will contain the diffe rent values 
as Object’s properties.  
 
Response  
All methods return a response object  with updated status of the corresponding inquiry, 
status or payments request. The information is contained within the object properties.

the actual reason.
