I. Paying Office Pickup Orders 
The purpose of these methods is to provide to the correspondent a service to pay office pickup orders in a 
fast, simple and safe manner. Following the instructions below will guarantee  the success of the 
correspondent’s integration with RIA. 
All the methods described in this section are mandatory to be developed in order to integrate with RIA for 
paying office pickup orders. RIA will test all the methods developed by  the correspondent in the test  
environment before to going live on the real environment.  
1 Web service methods  
 OP_VerifyOrderForPayout   (see appendix A for field types and code responses) 
 OP_ConfirmOrderPaid   (see appendix A for field types and code responses) 
 OP_VoidOrderPaidConfirmation  (see appendix A for field types and code responses) 
2 Verify orders (OP_VerifyOrderForPayout) 
 
In order to pay an Office Pickup order, the first step is to call the method OP_ VerifyOrderForPayout including 
the PIN of the order (e.g. 11313793692). This method is called to check if the order is available to be paid 
and to obtain information about the customer and the beneficiary. Also, this method returns  some fields like 
“TransRefID”, “OrderNo”, “BeneCurrency”,”BeneAmount”  that are needed in the request of method 
OP_ConfirmOrderPaid to confirm payment of  the order . The field “TransRefID” can also be used by the 
method OP_VoidOrderPaidConfirmation. 
The PayingCorrespID is a number that i dentifies the correspondent. It i s provided by RIA and is used for all  
requests. 
In case that the order is available to be paid this method returns the message “Order is available for payout” 
and the Response code is “1000”.

3 Pay orders (OP_ConfirmOrderPaid) 
 
Call the method OP_ConfirmOrderPaid  to pay the order  with information obtained from the 
OP_VerifyOrderForPayout response (TransRefID,PIN , OrderNo, BeneCurrency, BeneAmount). When this 
method returns a ResponseCode = 1000 and ResponseText = “Order confirmed as paid”, then the order is 
marked as Paid from RIA side.  
In this request,  information about the  beneficiary ( e.g. the document type, number of the document, the 
country where the document was issued, etc.) should be provided. The ID code or number that  identifies the 
location where the transaction was paid needs to be included in the CorrespLocID tag . At this point, RIA 
should know the ID number of all the locations of the correspondent where transactions will be paid . Using 
the information provided in this tag, RIA can know where each individual transaction is paid at.  
The method OP_ConfirmOrderPaid should be ca lled immediately after calling OP_VerifyOrderForPayout. This 
is necessary as  the service returns information on real time and  either RIA, or the sender, can change the 
order information between these two calls.

4 Void orders (OP_VoidOrderPaidConfirmation) 
 
The goal of method OP_Voi dOrderPaidConfirmation is to reverse the actions taken when calling  
OP_ConfirmOrderPaid in case that this method wa s not carried out correctly from RIA ’s side or 
Correspondent’s side. E.g. network interruption, network micro cut, power issue, etc. 
Once the method OP_VoidOrderPaidConfirmation is called, then the state of order from RIA changes from 
“Paid” to “Available for payout” once again.  
This method should be requested automatically without any intervention from the teller. The correspondent 
should mark the order as paid when  they receive the correct response from OP_ConfirmOrderPaid and not at 
the moment of the request.  
Keep in mi nd that the marking an order Paid on one side but not on the other can create a cascade effect 
that can consume a large amount of resources to correct the situation. This situation is easily solved by  
implementing OP_ VoidOrderPaidConfirmation correctly.  
There are two different scenarios where OP_VoidOrderPaidConfirmation should be called.  
The first one (Scenario A) happens when the correspondent calls OP_ConfirmOrderPaid and the web service 
return a TimeOutException, so the correspondent doesn’t know if  the order has been saved as paid by Ria. In 
this case,  the method OP_VoidOrderPaidConfirmation is called with the field OrderPaidTranRefID obtained 
from the field TransRefID of the response of method OP_VerifyOrderForPayout. If the service returns 
TimeOutException also in the method OP_VoidOrderPaidConfirmation, recall this method several times until a 
valid response is received.  
The second one (Scenario B) happens when the correspondent receive s a correct response of  
OP_ConfirmOrderPaid but receives an exception when try to save the order as paid in their database . In this 
case, the method OP_VoidOrderPaidConfirmation is called with the field OrderPaidTranRefID obtained from 
the field TransRefID of response of method OP_ConfirmOrderPaid. 
 
Note: This method can only be called within 2 minutes after calling the method OP_ConfirmOrderPaid.

II. PAYING BANK DEPOSIT TRANSACTIONS 
The aim of these methods is to make the process of bank deposit payment efficient and effective from the 
correspondent’s side. Developing these methods as indicated will avoid future problems between RIA and the 
correspondent. 
All the methods described in this section are mandatory to be developed in order to integrate with R IA for 
paying bank deposit transactions. RIA will test all the methods developed by the correspondent in the test 
environment before to go to real environment.  
1. Web Service methods 
 GetOrdersForDownload    (see appendix A for fields type and code responses) 
 GetCancelationRequests  (see appendix A for fields type and code responses) 
 InputOrderStatusNotices  (see appendix A for fields type and code responses) 
2. Downloading transactions (GetOrdersForDownload) 
The first method that needs to be called is  GetOrdersForDownload. This method will return all the 
transactions ready to be paid by the correspondent. This method should be called continuously.  By default, 
each transaction can only be downloaded once. The image below shows the request and the response of the 
method GetOrdersForDownload.

At the mom ent that transactions are downloaded, the correspondent  has to inform to RIA that those 
transactions have been received. This is done by calling the method InputOrderStatusNotices with the field 
OrderStatus = “RECEIVED”.  
 PCOrderNo is a unique ID provided by the correspondent to identify each order. 
 SCOrderNo is a unique ID provided by the RIA to identify each order. 
 NotificationID is a unique ID provided by the correspondent to identify each notification. 
 
 
 
3. Paying transactions (InputOrderStatusNotices) 
 
The payment of bank deposit transactions is done by calling the method InputOrderStatusNotices with the 
field OrderStatus = “PAID” and including also information related to the  beneficiary ( e.g. document type,  
document number, the country where the document was issued, etc.)  
Before the payment of any  transaction, method GetCancelationRequests should be called to get all the 
transactions that have been canceled by RIA , previously downloaded by the paying correspondent . In case 
that an order has been cancele d by RIA, that order cannot be paid. In that case the correspondent should 
call the method InputOrderStatusNotices with OrderStatus = “CANCELED”. 
The method GetCancelationRequests can be called con tinuously but it is important that it is  called before 
paying any order.  In the image below we can show that an order that was previously downloaded by the 
paying correspondent has been canceled by RIA or the sender correspondent.

4. Reject transactions (InputOrderStatusNotices) 
Bank deposit transactions can be rejected when the information is not consistent  or is wrong. This can be 
done by calling the method InputOrderStatusNotices with OrderStatus = “REJECTED” and giving a reason 
for that rejection.

V. CUSTOMER SERVICE MESSAGES 
The purpose of these methods is to offer the correspondent the ability  to communicate on real time with RIA 
Customer Service for any transaction paid. It also provides the correspondent the option of having a history log 
for any transaction and being informed of all the actions taken by Ria Cu stomer Service related to the orders 
paid. 
All the methods described in this section are mandatory to be developed by the correspondent in order to 
integrate with RIA. RIA will test all the methods developed by the correspondent in the test  environment 
before going to the live environment.  
1. Web Service methods 
 InputPayersCustSvcMsgs   (see appendix A for fields type and code responses) 
 GetSendersCustSvcMsgs  (see appendix A for fields type and code responses) 
2. Send messages to RIA (InputPayersCustSvcMsgs) 
Call method InputPayersCustSvcMsgs to send messages directly to RIA Customer Service Department related 
to orders paid by correspondent. These messages will be received by RIA Customer Service Department and 
will help RIA to make decisions and transmit the messages to the correspondent that sent the order.  
The method InputPayersCustSvcMsgs is combined with the method GetSendersCustSvcMsgs to create a way of 
communication through messages between Correspondent and RIA, for those orders that have been paid by 
Correspondent. 
Below is shown the request and the response of method InputPayersCustSvcMsgs. 
 PCOrderNo is a unique ID provided by the correspondent to identify each order. 
 MessageID is a unique ID provided by the correspondent to identify each Message.
