1. Overview & Background 
 
The transaction volume of RTGS has been significantly increased and is expected to be increased further due to the decision t aken by 
SBP to allow customers’ funds transfers for lower limits. Therefore, considering the increasing trend in RTGS transfers SBP has initiated 
STP project to automate the RTGS payments to minimize manual workload of customers’ requests for RTGS. 
 
This will not only help us in reducing the TAT due to duplicate efforts put in by the relevant depa rtments due to manual posting in core 
banking system and PRISM but will also help us in improving our processing capabilities to manage additional transactional vo lume 
within the window allowed by SBP for RTGS payments. 
 
Straight through Processing (STP) is an initiative used in the financial world to optimize the speed at which transactions are processed. 
This is performed by allowing information that has been electronically entered to be transferred from one party to another in  the 
settlement process without the need for re-keying the same pieces of information repeatedly over the life cycle of the transaction. 
 
About RTGS System 
RTGS system started its operations in July 2008. Since its inception, enrollment of the participants is growing and volume of transactions 
is also increasing.  
 
Payment System Department has also introduced Customer Transfers (MT103) and Multiple Credit Customer Transfer (MT102). This has 
further increased volume of transactions.

Currently, RTGS Participants are entering transactions in RTGS system manually using RTGS Client workplaces installed at their own 
premises. Same transactions they also have to re-enter in their Core Banking System through its own workplaces. Multiple re-keying is 
inefficient and error prone. Soon it will also be impractical to enter all these transactions manually due to increase in volume. 
 
Therefore, it was decided to introduce STP (Straight Through Processing) to deal with the above mentioned issues. STP will electronically 
connect Participant Core Banking system with RTGS system using standard interfaces that are already provided with the RTGS system. 
 
In this connection, Participants needs to develop an Integration Software that can pick up information from their Core Banking System 
and transfers it to RTGS system for processing and vice versa.

2. Bank Requirement Scope 
 
However, since the bank has opted option of File Adapter without “Controller”; therefore it is essential to develop “INTEGRAT ION 
SOFTWARE” to cater the need of “controller” which curren tly provided by SBP as part of PRISM to perform multiple functions, which 
includes but not limited to authorization of MT102, MT103, MT202, Balance enquiry, monitoring of inflows and outflows, free f ormat 
messaging and any other functionality which is currently available in the PRISM Controller provided by SBP. 
 
The integration software should have the capability of interfacing with partner applications i.e. Remit Home System, CMS Application, T-
24 and any other application which requires to be integrated with integration software. 
 
Upon receiving the RTGS instructions from any of the partner application, the integration software, should convert the messag e based 
on its payment type (as per SBP’ prescribed formats of MT -102, MT-103 and MT-202) and push the outward MTs to PRISM by following 
all the relevant protocols to meet SBP’ requirements. Similarly, the integration software should have the capability to recei ve incoming 
RTGS received via PRISM from other banks for various departments/customers of the bank.

4. Integrator and Core banking modules  
i- Integration through RTGS-Integrator’s provided APIs  
1. Core banking modules (Home remittances etc) will send data by calling API method provided by RTGS-Integrator. 
2. Core banking modules will get data acceptance response from RTGS-Integrator, acknowledging that transactions have been 
received. 
3. Core banking modules will get the status information of the data send by calling status method of RTGS-Integrator. 
4. Core banking modules (Home remittances etc) will get data by calling API method provided by RTGS-Integrator. 
5. Core banking modules can update the status of transactions that they have received (Incoming transactions) by calling API 
method. 
6. Note: For remit home application a windows service will be developed by Centegy that will keep on checking the statuses of the 
data sent to RTGS-Integrator.

5.    Specification of the RTGS Integrator 
 
- Integrator application will expose its API methods to the banking modules like (Remit home etc). 
- These banking modules will call the API methods exposed by Integrator to send and receive data. 
- T-24 will be acting as a separate module/application and will integrate with Integrator through Files folders. 
- Integrator will integrate with T-24 according to JSBL’s provided/decided file format for sending/receiving data. 
- Integrator will keep on reading File out folder to get data to be processed. 
- Integrator will create a file and park it in the File In folder from where T-24 will read the data. 
- There will be no acknowledgement file creation/reading concept. 
- File once processed will be forwarded to the archive folder. 
- Integrator will have a start of day and end of day features, before the start of day no processing will be performed and similarly after end 
of day activity no processing will be performed on that particular day. 
- Integrator will have an optional authorization screen/layout for both Inward and outward transactions. From where user can 
release/amend/adjust/cancel transactions. 
- Release means transactions are allowed to be processed further. 
- Amend means transactions in the MT file can be amended (only demographic information). 
- After amendment authorization, MT containing that particular transaction will be available at the layout mentioned at point 11. 
- Adjust means forcefully ended now MT will not be processed further and will be displayed as forcefully processed. 
- Cancel means no further processing. 
- MT 102, 103, 202, 900, 910, 199 are the part of covered scope. 
- SBP/RTGS/PRISM integration will be based on RCCC method. 
- No reversal mechanism.
